格納方式の選択肢

案仕組み評価
A. Git LFS（第一案） .gitattributes に *.pt filter=lfs。clone で実体取得 推奨。「stored in the repository」を最も素直に満たす標準方式。quota: storage 1GB・帯域 1GB/月（審査 clone 数回なら許容圏）
B. チャンク分割 + 再結合 141MB を <100MB に分割して通常 blob コミット、notebook で連結復元 LFS quota 不要だが体裁が悪い・sha 検証は復元後に実施。LFS 不可時のフォールバック
C. fp16 化 重みを半精度にして ~70MB 非推奨 — reviewed バイトの SHA256 provenance を失い、推論結果が変わりうる
D. Release assets GitHub Release に .pt を添付（2GB/ファイル可） 「repository に格納」の解釈次第で不適合リスク。LFS の代替としてのみ検討

4. どうすればいいか — 対応プラン

  1. weights-only エクスポートを作成・指紋登録
    plain_mhsa_f2 は best_model state_dict のみ抜き出して 141MB に半減。 新しい SHA256 を provenance manifest に登録（推論 byte 等価を OOF で確認）。 既存 b1c0f353... 等の reviewed SHA は正本として維持。
  2. standalone repo（solar-filament-2026-solution）に LFS 設定
    .gitattributes に LFS ルールを追加し weights/ ディレクトリに配置。 ※ repo は現在 private — push しても外部には見えないため事前作業に支障なし
  3. repro notebook の重み解決を更新
    優先順: ① repo 内 weights/ の相対パス → ② （フォールバック）Kaggle dataset 参照。 両方に対応させ、LFS clone 環境では ① が使われることを確認
  4. 締切日（11-15）に公開化 + ログアウト検証
    gh repo edit --visibility public → 匿名 clone で LFS 実体が降りること、 notebook が repo 内重みで完走することを確認
  5. Kaggle dataset 公開は補助として残置
    LFS 帯域 quota が枯れた場合や審査員の clone を介さない再現経路として。 「repo 内格納が正本、dataset は冗長経路」とレポート/README に明記
  6. Google Form 送信（ユーザー操作）
    repo URL + レポート PDF。再提出は最大10ファイルまで可（749524）— 最終版 PDF と合わせて確認
タイミングについて: LFS 同梱・notebook 更新・provenance 登録は 今から先行作業可能（private repo のまま push 可能）。公開化・ログアウト検証・ Form 送信だけが締切日のユーザー操作として残る。
残リスク: LFS 帯域 1GB/月は審査で複数人が clone すると枯渇しうる （~420MB × 数回）。枯渇時は LFS オブジェクトが pointer のまま降りるため、 フォールバックの dataset 参照経路と、README への「LFS 失敗時は dataset から」 という記述を保険として残すのが実務的。
