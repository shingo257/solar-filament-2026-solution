0. エグゼクティブサマリ

敗因は検出器ではなく「選択」 — しかも我々はその事実を測らないまま終わった。

  • マスク品質(SQ)は上位陣と互角(0.681 vs 0.683-0.688)。差のほぼ全ては認識品質 RQ(0.672 vs Guillaume 0.708) = どの候補を残し/落とすかの判断精度
  • 全上位チームが到達した結論: 候補プールは注釈フィラメントの ~90% を既に含有し、oracle 選択で 0.56-0.62 に達する。実用スコアとの差 0.1 近くは全て「選択層」にある — 我々のプールで事後実測: oracle 0.586・実用 0.458・選択ギャップ +0.128(11/27 計測)。プール自体は top-20 級だったことが証明された
  • 我々は oracle 選択実験を一度も行わず、最終週を検出器側の改良(天井 +0.002〜0.006)に費やした。選択層の改善余地(+0.1)に気づくための唯一の実験を欠いていた
  • それでも private 0.37 は公開手法の中央的水準 — 検出器多様性合意の洞察自体は正しく、誠実な検証基盤(漏洩摘発・clean repro 99.91%)は上位陣に見劣りしない

2. 6つのギャップ(推定影響度順)

Gap 1 — 学習型「候補採点器」が存在しなかった決定的

上位陣ERS
候補の採点LightGBM / CNN judges / PQ½-verifier で候補ごとの PQ 寄与を回帰予測(Guillaume: 相関 0.780)固定 conf ≥ 0.26 + 2-of-3 合意ルール。候補の「品質」をデータから一切学習していない
理論的裏付け「候補は期待 matched-IoU が PQ/2 を超える時だけ得」— τ≈PQ/2 をmetric の式から導出閾値はグリッド探索でのみ決定
特徴量幾何・強度・soft-mask 統計・画像文脈・モデル間一致・view 安定性detector の conf のみ

定量証拠: Guillaume の ablation で採点器+厳密選択の導入が +0.005(0.4693→0.4739)、さらに特徴量強化で +0.002。oracle との差を考えると真のポテンシャルは +0.01〜+0.10 規模。我々の全改善(spine+small-TAL+consensus)の合計 +0.009 を、この1要素で上回れた可能性がある。

Gap 2 — oracle 選択実験を一度も測らなかった戦略的敗因

コンペ全体を通じて最も重要な1行の計測 — 「自分の候補プールから全知選択したら PQ はいくつか」 — を我々は一度も行わなかった。事後計測(11/27)の結果: union3 oracle 0.586、実用値との差 +0.128 — 仮説は完全に裏付けられた。

  • もし v120 時点(11/9)で測っていれば: union3 arm(emitted 13/img)の oracle 天井が 0.58+ と分かり、「検出器改良は天井が低く選択学習こそ本線」と最終週の全リソース配分が変わっていた
  • 実際にやったこと: v120-125 で consensus 後処理の精緻化(全滅)→ v130-137 で検出器改良(天井 +0.002-0.006)に終始
  • 上位4チームは全員この測定を行い、その結果に従ってパイプライン全体を「選択中心」に設計した。測定が設計を駆動した好例

教訓: 改善余地の大きさを測ってから改善先を選ぶ。「どこにギャップがあるか」は直感ではなく oracle/ablation で先に定量すべきだった — 我々の prereg 文化(事前登録・ゲート)は正しかったが、登録する問いの選択を間違えた。

反証ではなく傍証: 同じ YOLO 系でも Artem は 2048+1280 マルチスケール+WBF で fold-0 val 0.462(private 0.38)に到達 — YOLO であっても適切な解像度なら 0.38 層に届いた。我々の v116 crop tile 線は native 解像度を狙った正しい方向だったが、漏洩バグで失格となり修正版が最終提出に間に合わなかった(最終 trio は prod/yolo26/sptal で crop det 非含有)。

Gap 4 — 厳密な非重複選択(整数計画/木DP)大

  • 上位陣: 候補集合から Σ(q−τ) を最大化する非重複部分集合を厳密に解く(小さな整数計画 / exact Tree-DP)。「1本丸ごと A」vs「2片 B+C」の選択で、貪欲法は A を取るが厳密解は B+C が得なら両方取る
  • ERS: 貪欲な占有ベースの重複解消(pixel-disjoint は達成、ただし最適性は非保証)。merge/split 後処理は v128 で検証し陰性で閉鎖 — だが厳密選択は別物であり、こちらは未検証のまま

Gap 5 — 多 view TTA 合意の欠如中

  • 上位陣: 1モデルあたり 8-16 view(flip+回転)を推論し view 間で合意。候補の「view 安定性」自体が採点特徴量にもなる
  • ERS: 単 view × 3 アーキテクチャ。多様性はモデル族間に依存し、view 軸の多様性は未使用(v140 で hflip stream を検証したが最終提出には未採用)

Gap 6 — アノテータ target 設計中

  • 上位陣: soft consensus target(画素ごとに「アノテータの何割が描いたか」)でモデルに不確実性を学ばせる(Zhu/Organokov)、または epoch ごとに1アノテータをサンプルし個人の輪郭を学ばせる(Artem)
  • ERS: 主に hard target。soft_w50 変体は僅かに良好(0.45213 vs 0.45195)だったが差を検証せず maj3 を採用 — 少数点以下の差を追う余裕がなかった

5. 反実仮想 — v120 時点で勝ち筋に乗るには

  1. Day 1: union3 候補プール(emitted 13/img)の oracle 選択 PQ を測定 → 0.55+ を確認し「選択が本線」を確定
  2. Day 2-3: 候補プール拡大(多 conf・多 view・多モデルの union、FP コスト無視 — 選択器が処理する)
  3. Day 3-5: 候補ごとの特徴量(幾何/強度/soft統計/モデル間一致/view 安定性)+ LightGBM で対アノテータ IoU 回帰。cross-fit で fold 厳密化
  4. Day 5-6: τ≈PQ/2 の理論導出 + 非重複厳密選択(連結成分ごとの小整数計画)
  5. Day 6-7: 全解像度 U-Net で境界 2px 再描画(我々の refiner は既に crop 再描画を持っていた — 方向転換は容易だった)

既存資産の再解釈: spine 教師・small-TAL・consensus は候補プールの多様性を上げる部品としては正しい投資だった — ただしそれらを「最終出力のフィルタ」として使ったのが誤りで、「選択器への入力特徴」として使うべきだった。

5.5. 反実仮想の実測検証 — 「選択層を学習するだけ」では勝てなかった(2026-11-28 追記)

上記の処方箋が正しいか、実際に我々の候補プールで検証した。v140 oof cache の union3 プール(fold0/2・471 画像・8,737 クラスタ)に対し、detector 合意・conf・幾何・強度・view 安定性の 19 特徴量で LightGBM 採点器を学習し、fold 相互 cross-fit の honest 評価で公式 PQ を測定:

選択方式fold0 PQfold2 PQ判定
consensus ルール(≥2det@0.26、現行提出の系)0.44850.4478ベースライン
LightGBM 直接 IoU 回帰(Guillaume 式、τ cross-fit)0.42860.4287−0.020 劣化
LightGBM two-head h×m(taitran 式)0.42630.4271−0.021 劣化

結果は陰性 — しかしこの失敗の診断こそが本質的な教訓:

  1. score-target 相関は 0.45-0.50 に留まった(Guillaume の報告 0.78 と大差)。しかも train fold 内で τ を最適化してすら PQ 0.433 止まり — 過学習ではなく特徴量の情報量が根本的に不足している。勝者は 16-view 推論安定性・semantic 確率マップ質量・10 seed 平均の特徴を持ち、我々の 19 特徴では detector 合意ですら重要度下位(上位は cent_r/extent/log_area 等の幾何・強度に支配)
  2. singleton(1 detector のみ)の 42.6% は正当な TP — consensus ルールが捨てている TP 層は実在し、そこにこそ選択学習の価値があるはずだったが、今の特徴では「良い singleton」と「悪い singleton」を分別できない
  3. 結論の修正: ギャップ 1「学習型採点器の欠如」は正しいが、それは表層だった。真のギャップは「選択を学習可能にする特徴基盤」— 多 view 推論コスト(16 回/画像)・semantic 確率マップ出力・大規模 ablation 検証 — を設計段階から用意していたかどうか。LightGBM 自体は商品ではなく、その前提条件の上にのみ機能する。つまり勝者との差は 1 つのモジュールではなく、パイプラインの情報アーキテクチャ全体だった

追補(singleton 救済ハイブリッド): consensus ルールを基底に singleton のみをスコアで救済する設計も検証したが、train fold 内で救済閾値を走査してすら pure consensus を超えられない(best 0.4457/0.4476 vs pure 0.4471/0.4477)。全 τ で劣化・τ を下げるほど単調に悪化 — 我々の特徴基盤では学習スコアの利用価値は完全にゼロと確定。

検証コード: C:/work/solar_counterfactual/(build_selection_dataset.py・eval_learned_selection.py、8,737 クラスタ・圧縮 RLE ドメイン評価)。なお oracle 天井 0.586 と実用 0.458 の差 +0.128 が「適切な特徴基盤でのみ回収可能なポテンシャル」であることは変わらない — ただしその回収は我々が想定したより遥かに重い設計投資を要求する。

6. 次のコンペへの教訓

  • 最初に oracle を測れ: パイプライン各段の「全知天井」を週1で測り、最大ギャップの段にだけ投資する。改善は天井の大きい順にやる — ただし天井を回収する手段のコストも見積もれ(§5.5: 選択学習は特徴基盤ごと必要)
  • metric の式を読め: PQ/2 採用条件のように、最適解の構造は metric の代数から直接導けることが多い。上位陣は全員ここから設計していた
  • 生成と選択を分けよ: 生成は recall 最大化(FP 無視)、選択は学習で。両者を1つの閾値で兼ねる設計は両方を劣化させる — 我々の conf 0.26 まさにそれ
  • preprocess/解像度は physics から決めよ: 11px 幅の構造に 1.6× 縮小は metric の崖と衝突する。対象の物理スケール ÷ IoU 閾値で必要解像度は計算できる
  • 誠実な検証基盤は守り続けよ: 今回の唯一無二の成果は、漏洩摘発・prereg・clean repro・人間ベンチマークという検証文化 — これは勝ったチームの多くより強かった資産

7. 勝者手法の原典調査 — 知識ギャップの正体特定(2026-11-28 追記)

ギャップ (c)「方法論の知識」の具体的な正体を、一次資料の文献調査で特定した (ml-literature-dig ワークフロー、詳細は DL-skill の selection-architecture-literature.md に永続化)。

勝者手法の各要素は発明ではなく文献の適用だった

勝者手法の要素原典・実装アンカー
確率マップの成分木(component tree)Salembier 1998 / Jones 1999 / Berger 2007(数学形態学)+ higra ライブラリに max_tree・extinction values の実装あり
木上の厳密選択(Tree-DP)dp(u) = max(score(u), Σdp(children)) の O(|V|) 定式 + tree-cut 文献(arXiv 1506.03852/1505.06389)
候補採点の学習Hosang CVPR 2017「Learning Non-Maximum Suppression」— detector は複数高スコアを出す設計なので選択は joint 処理が必須、という問題分析の原典
選択回避型デコード(代替)StarDist / HoVer-Net / Cellpose — 混雑インスタンスをピクセル表現で分離。filament は非凸なので star-convex は不適合、flow 系は転用余地

調査の最大の発見 — 欠けていた特徴には30年前の定式があった

§5.5 で「我々の特徴に無く勝者にあったもの」として特定したレベル間・view 間の安定性特徴は、 数学形態学の文献では extinction value / persistence として既に定式化され、 higra に実装まであった。つまり勝者の優位は発明ではなく正しい文献を知っていたことであり、 我々の敗因 (c) は「探し方を知らなかった」ではなく「探すべきものが何かを知らなかった」 に帰着する — oracle 計測をしていれば「選択のための安定性特徴」という探索目標自体が 生まれていたはずで、敗因 (a)(oracle 未計測)が敗因 (c) を生んだ連鎖構造が見える。

実装ロードマップ(次回そのまま実行可能)

  1. 確率マップ出力モデルを用意(semantic 系または instance 系の内部確率)
  2. higra またはレベル閾値スキャンで成分木を構築
  3. ノード特徴(確率質量・extinction/persistence・多 view/seed 一致度・幾何)で expected-IoU 寄与を LightGBM 学習 — cross-fold honest 評価
  4. Tree-DP で厳密選択(採用判定は PQ/2 理論値)
  5. 選択後の境界を全解像度で再描画

各段の間に oracle 計測を挟み、ギャップが最大の段にだけ投資する (§5.5 の実験が示す通り、特徴基盤なしで 3-4 から始めても失敗する — 順序が本質)。
